Section 0 — The two companies

Apple — the control

Apple has been continuously listed on NASDAQ since its December 1980 IPO. Over a 30-year window it gives you one PERMNO, one GVKEY, one exchange, one CUSIP, and one ticker. Five things follow, and they are the whole reason Dell is in this lab.

Dell did not "relist." There was no re-IPO and no new public offering of Dell common stock in 2018. The Class C shares became publicly traded because Dell Technologies bought in the Class V tracking stock, paying partly in Class C shares, which then listed.

CRSP says three securities; Compustat says one company. Two of them are Dell common stock — old Dell and Class C — with the Class V tracking stock in between. Old Dell and Dell Technologies are different PERMNOs (11081 / 18267), different PERMCOs (9833 / 55676), different CUSIPs, and different exchanges (NASDAQ / NYSE). But Compustat carries one GVKEY, 014489, through the whole history — still costat = 'A', still carrying the 1988 ipodate. Neither vendor is wrong. They are answering different questions, and the CCM link table is where the two answers meet.

The ticker string carries over, and that is the trap. WHERE ticker = 'DELL' returns both securities. Sorted by date they look like one series with a five-year hole. Nothing errors. You will build this trap deliberately in Step 3.8.

DVMT is not Dell for the missing years — but CRSP does record a succession. The Class V stock tracked the economic performance of Dell's interest in VMware, so using it as "Dell 2016–2018" answers a question about VMware and labels the answer Dell. What CRSP does record is nwperm = 18267 on DVMT's delisting row: a Class V holder became a Class C holder. So a defensible DVMT → Class C series exists. What does not exist, anywhere in the data, is any link from old Dell to anything: nwperm = 0.

The delisting return is small and positive. dlret = +0.94% for a take-private at $13.86 against a September close of $13.75. The interesting number is not its size; it is that it exists at all, and that the SIZ monthly file's October 2013 row is otherwise empty — prc, ret and retx are all null and cfacpr is 0.

The rule this gives you. A gap in a price series is a fact about the security, not a defect in the data. Filling a gap that reflects a real discontinuity does not repair the panel; it destroys the only evidence that the discontinuity happened.

import pandas as pd, psycopg2, os

                      user=WRDS_USER, sslmode='require', connect_timeout=30)

def raw_sql(sql, params=None, date_cols=()):
    # drop-in substitute for conn.raw_sql where pandas' SQL path fails
    with cn.cursor() as cur:
        cur.execute(sql, params)
        df = pd.DataFrame(cur.fetchall(), columns=[c[0] for c in cur.description])
    for col in date_cols:
        df[col] = pd.to_datetime(df[col])
    return df

1.3 Credentials

The PostgreSQL server does not accept institutional single sign-on. It authenticates a WRDS-native password through PAM. If you have only ever reached WRDS through the Purdue login, you probably do not have one, and the failure reads:

FATAL:  PAM authentication failed for user "yourname"

That is a rejected password, not a broken config. Set one under Account → Profile on the WRDS website and allow a few minutes for it to propagate.

Then create ~/.pgpass — on Windows, %APPDATA%\postgresql\pgpass.conf — containing one line:

wrds-pgdata.wharton.upenn.edu:9737:wrds:YOUR_USERNAME:YOUR_PASSWORD

and set the permissions, or the driver ignores the file:

chmod 600 ~/.pgpass

A literal : or \ inside the password must be backslash-escaped, or the line parses into the wrong fields and you get the PAM error above with a password that is actually correct.

With that in place, connecting needs no prompt and puts no secret in your notebook:

import wrds
conn = wrds.Connection(wrds_username='YOUR_USERNAME')

Never type a password into a cell. Never commit a notebook containing one. Close the connection when you are done — WRDS is a shared server with a finite pool:

conn.close()

1.5 The cache pattern

Use this for every pull in this document. It is four lines and it is the difference between a notebook you can iterate on and one that costs 90 seconds of shared server time per run.

import pandas as pd

def cached(name, fn, refresh=False):
    """Run fn() once, cache to Drive as Parquet, reuse thereafter."""
    path = PROJ / 'raw' / f'{name}.parquet'
    if path.exists() and not refresh:
        print(f'{name}: cache hit -> {path}')
        return pd.read_parquet(path)
    df = fn()
    df.to_parquet(path, index=False)
    print(f'{name}: pulled {len(df):,} rows -> {path}')
    return df

Your final submitted notebook must still run start to finish on a fresh kernel (rules.md). A cache that is read but never demonstrably regenerable is not reproducible — so keep the refresh=True path working and say in the notebook when you last used it.

1.6 Schema reconnaissance — do not skip this

This is the step that separates a working query from an hour of UndefinedTable errors. CRSP has been migrating from its legacy file layout to a newer one. CRSP's own names for the two are SIZ (the legacy layout: crsp.msf, crsp.msenames, crsp.msedelist) and CIZ (the current one: crsp.msf_v2, crsp.stksecurityinfohist). Treat them as labels — what matters is that they hold the same data under different column names and, in one important case, different conventions. Which you have, and which tables your account actually exposes — and what the columns inside them are called — depends on your institution's subscription and the vintage of the data on the server. The column names in Sections 2 and 3 are the SIZ names, because they are what nearly every textbook, replication package, and WRDS example is written in. Confirm what you have:

Section 2 — From CUSIP to permanent identifiers

2.1 What a CUSIP actually is

Nine characters, in three parts:

The first six identify the issuer. The next two identify the specific issue — a class of common stock, a particular bond, a preferred series. The last is a computed check digit carrying no information.

This matters immediately, because the two databases store different amounts of it:

DatabaseFieldLengthNote
CRSPncusip8Historical — the CUSIP that was correct at the time of that name record
CRSPcusip8Header — the security's most recent CUSIP, stamped on every historical row
Compustatcusip9Current, includes check digit

So a 9-character CUSIP from a 10-K cover page needs the check digit dropped before it will match anything in CRSP:

def cusip8(c):
    """9-character CUSIP -> the 8-character form CRSP stores."""
    c = c.strip().upper()
    return c[:8] if len(c) == 9 else c

2.2 The header-CUSIP trap

crsp.msenames has both ncusip and cusip, and they are not the same thing.

  • ncusip changes through the security's life, one value per name record.
  • cusip is the current value, copied onto every row including rows from 1994.

Search on cusip and you will find a security by its present identifier even for periods when it had a different one — which sounds convenient and is exactly the look-ahead the course spent Week 1 on. Search on ncusip and you find it by what it was actually called at the time. Query both, compare, and understand why they differ before you pick one.

2.3 Find the PERMNO

import pandas as pd

Gotcha that will cost you ten minutes. Two rules, both verified against the library source rather than inferred. (1) raw_sql uses pyformat placeholders — %(name)s, not :name. It hands your string to pandas.read_sql_query, which calls SQLAlchemy's exec_driver_sql, which passes it straight through to psycopg2; the :name style that SQLAlchemy's own text() would want never applies. The wrds package documents exactly this style in its own raw_sql docstring. (2) The parameter for an IN clause must be a tuple, not a list. psycopg2 renders a tuple as (a, b) and a list as a PostgreSQL array, and an array on the right of IN is a type error. A one-element tuple needs the trailing comma: (14593,). WRDS's own published examples sidestep both by writing literal values into the SQL string. That is fine for fixed dates and dangerous for anything derived from input. Parameterise.

2.4 Find the old Dell — search by name, not by identifier

You do not have old Dell's CUSIP, and this is the realistic case: you have a company, not an identifier. Search the name history.

dell_names = conn.raw_sql("""
    SELECT permno, permco, namedt, nameendt, ncusip, cusip, ticker, comnam,
           shrcd, exchcd
    FROM   crsp.msenames
    WHERE  comnam LIKE 'DELL%%'
    ORDER  BY permno, namedt
""", date_cols=['namedt', 'nameendt'])

print(dell_names.to_string(index=False))

comnam is stored uppercase. Note the doubled %%: the database driver reads a single % as the start of a parameter placeholder, so a literal one in a LIKE pattern must be escaped. Doubling works; passing the pattern as a parameter — LIKE %(pat)s with params={'pat': 'DELL%'} — is cleaner and always safe.

You should get more than one PERMNO. Sort out which is which by namedt/nameendt and by exchcd, and expect to see at least: the NASDAQ security whose name records end in 2013, the NYSE Class C security starting December 2018, and — if your search is loose enough — the Class V tracking security running from 2016 to 2018. Confirm the tracking stock's identity by its comnam and its share class field rather than by assuming.

3.3 Splits: cfacpr and cfacshr

prc is the price as traded on that date, unadjusted. Apple traded above $600 in 2012 and near $100 in 2014, and nothing happened to the company in between except a 7-for-1 split. Plot raw prc over 30 years and you will produce a chart that is simply false.

CRSP gives you two cumulative adjustment factors:

  • cfacpr — cumulative factor to adjust prices
  • cfacshr — cumulative factor to adjust shares outstanding
msf['prc_adj']    = msf['prc_abs'] / msf['cfacpr']
msf['shrout_adj'] = msf['shrout']  * msf['cfacshr']

The adjusted price is expressed in the units of the most recent period in the file — that is what "cumulative" means — so the whole series shifts when CRSP updates. An adjusted price is a relative quantity. Never quote one as a historical fact without saying what it is adjusted to.

Verify the adjustment on a known event. Apple's 7-for-1 split took effect in June 2014. Print the four months around it:

      [['date', 'prc', 'prc_adj', 'cfacpr', 'ret', 'shrout']].to_string(index=False))

When the two factors disagree — the case that breaks naive code

3.4 Market capitalisation

# shrout is in THOUSANDS of shares; prc is in dollars.

Use the unadjusted price with the unadjusted share count. Market cap is a level, and levels are invariant to split adjustment — dividing the price and multiplying the shares by the same factor cancels. Applying only one of the two adjustments is a common and large bug.

That mask line is not decoration. Without it, a month where both fields are missing becomes a return of exactly 0.0 — a fabricated observation that no null-count will ever find. That is the Week 2 failure mode reproduced inside your own cleaning code.

When dlret itself is missing. If you apply a substitution, say so on the face of the result, cite it, and report the statistic both ways. If you do not, say that too. What is not acceptable is dropping the row, which deletes the worst outcome in the security's history and biases every subsequent statistic upward.

In the CIZ layout, the delisting return is already in the return series. WRDS states this directly in its own published Fama-French replication for the new format (ff3_crspCIZ.ipynb, the CRSP block):

No need to add delisting return in the new CIZ CRSP format — last trading return and price prior to delisting are already part of the time series output.

  • Dell closes at the end of January. fyr = 1, offset 1 on every row in its history. The twelve months ending 2019-01-31 are what Dell's own annual report calls fiscal 2019; Compustat labels that row fyear = 2018.

So Dell fiscal 2024 and Compustat fyear 2023 are the same twelve months. Merge on fyear against anything keyed to Dell's own reporting language and you are off by one year for the entire history. Always join on datadate. Use fyear for labelling only, and when you write about a Dell figure, say which convention you are using.

This single gotcha, on a company where the offset is 1 in every year, is worth its own data_quality_issues.md entry.

4.5 Derived quantities, and where they break

import numpy as np

# Preferred stock, in the standard order of preference
f['pref'] = f['pstkrv'].fillna(f['pstkl']).fillna(f['pstk'])

# Book equity: SEQ, else CEQ + PSTK, else AT - LT; then + deferred taxes - preferred
f['be'] = (f['seq']
             .fillna(f['ceq'] + f['pstk'].fillna(0))
             .fillna(f['at'] - f['lt']))
f['be'] = f['be'] + f['txditc'].fillna(0) - f['pref'].fillna(0)

f['leverage'] = (f['dltt'].fillna(0) + f['dlc'].fillna(0)) / f['at']
f['roa']      = f['ib'] / f['at']

      .to_string(index=False))

The version above adds the ceq + pstk and at − lt fallbacks for seq, which matters on older or sparser records. Either is defensible; state which you used.

For any year with negative book equity:

  • book-to-market is still arithmetically defined, and negative equity is genuine information about the balance sheet — but the ratio stops ordering firms the way a value signal is supposed to;
  • ranking on it puts the company at one extreme of the cross-section for a reason that has nothing to do with being cheap;
  • the standard convention in portfolio construction is to exclude non-positive book equity — WRDS's own Fama-French code sets it missing. Adopt that, or don't, and say which.

Whatever you find, report the count: "book equity is negative in N of M firm-years (X%)". That is the evidence standard in rules.md.

4.6 What funda is not: point in time

Week 2's Part 4 demonstration measured a 34-day gap between Apple's period end and its filing date. comp.funda does not close that gap for you, in two distinct ways:

  1. No filing date. The annual file gives you datadate, not the date the figures became public. The quarterly file comp.fundq carries rdq, the earnings report date, which is the closest thing Compustat gives you to a knowability date. Otherwise you go to EDGAR through the cik you pulled in Step 2.6.
  2. Not a point-in-time vintage. Standard funda may carry values that were updated or restated after the fact, so it cannot tell you what a figure looked like to an investor on a given historical date. Compustat sells separate point-in-time products precisely because the standard annual file is not one.

So the lag policy Lab 2 Step 5 asks you to choose is not a formality — it is the only thing standing between your panel and look-ahead bias. Pick a number of days after datadate before you treat a fundamental as knowable, defend it against one alternative, and apply it mechanically in Section 5. There is no correct number. There is a defended one.

Section 5 — CCM: joining prices to fundamentals

5.1 Why a link table exists at all

CRSP is a security database keyed on PERMNO. Compustat is a company database keyed on GVKEY. The relationship between them is many-to-many and it changes over time: one company can have several listed securities, a security can be transferred between registrants, and both vendors reuse neither key across entities. There is no join key. There is a curated link table, maintained by CRSP, that records which GVKEY corresponds to which PERMNO over which date range.

Joining on CUSIP or ticker instead is the classic shortcut and it fails on exactly the cases this lab is built from.

5.2 The link table and its two filter columns

Two link tables are in circulation and your subscription may expose either or both: crsp.ccmxpf_lnkhist (the link history file) and crsp.ccmxpf_linktable (the flattened view, which is what WRDS's own current Fama-French example queries). Check Step 1.6's table list and use what you actually have; the columns used below exist in both.

def pull_link():
    return conn.raw_sql("""
        SELECT gvkey, lpermno AS permno, lpermco AS permco, liid,
               linktype, linkprim, linkdt,
               COALESCE(linkenddt, CURRENT_DATE) AS linkenddt
        FROM   crsp.ccmxpf_lnkhist
        WHERE  gvkey IN %(g)s
        ORDER  BY gvkey, linkdt
    """, params={'g': GVKEYS}, date_cols=['linkdt', 'linkenddt'])

link_all = cached('ccm_lnkhist', pull_link)
print(link_all.to_string(index=False))

One GVKEY, two PERMNOs, and a five-year hole. 014489 links to old Dell through 2013-10-31, then to Class C from 2018-12-28. Between those dates the link table supplies nothing. DVMT has no link at all. PERMNO 16267 does not appear. Apple's link is LU, Dell's are LC. Unresearched versus research-complete, on the two most heavily studied companies in the file. This is why the standard filter keeps both; a linktype = 'LC' screen would silently drop Apple.

5.5 The monthly analytical panel

Now merge fundamentals onto the monthly price panel, applying your lag policy. Two rules govern the merge:

  • Use the most recent fundamental that was knowable as of that month — never the one whose datadate is nearest, which can be in the future.
  • Impose a tolerance, so a stale fundamental is not carried forward indefinitely when a company stops filing.

Before you merge, normalise the identifier dtype on both sides. wrds returns columns using pandas' nullable extension types, so permno arrives as Int64 (capital I) from CRSP, while the link table's permno is a plain int64 after your cast. They look identical when printed and merge_asof refuses them:

pandas.errors.MergeError: incompatible merge keys [0] Int64Dtype() and dtype('int64'),
must be the same type

This one at least fails loudly. Fix it once, for every frame:

for df in (m, fl):
    df['permno'] = df['permno'].astype('int64')
LAG_MONTHS = 6      # your Lab 2 Step 5 policy. State it. Defend it. Apply it mechanically.

fl['avail_date'] = fl['datadate'] + pd.DateOffset(months=LAG_MONTHS)

left  = m.sort_values('date')
right = (fl[['permno', 'avail_date', 'datadate', 'fyear', 'at', 'be',
             'sale', 'ib', 'leverage', 'roa']]
         .sort_values('avail_date'))

panel = pd.merge_asof(
    left, right,
    left_on='date', right_on='avail_date',
    by='permno',
    direction='backward',
    tolerance=pd.Timedelta(days=550),      # measured from avail_date - see note below
)

panel['bm'] = panel['be'] / panel['mktcap_musd']
panel.loc[panel['be'] <= 0, 'bm'] = np.nan          # negative book equity -> undefined

Both frames must be sorted by the merge key globally, not within groups — merge_asof requires it and the error message when they are not is unhelpful.

Why the tolerance matters: without it, the last fundamental before a company stops filing is carried forward to every subsequent month. Over a five-year gap that produces a B/M ratio in 2018 built from a 2013 balance sheet, and it looks like a number.

Read the tolerance carefully. 550 days is measured from avail_date, which is already datadate + 6 months — so a fundamental can stay attached for roughly two years after the fiscal period it describes, not eighteen months. That is deliberate for annual data, where the next observation is a year away. Know which date your window is anchored to before you quote it.

Two further conventions you are adopting by running this cell, both worth one line in your notebook. The link is validated at datadate — "was there a linked security at fiscal period end" — which is a defensible period-end rule, not the only one; validating at avail_date answers a slightly different question. And bm divides an annual book equity by that month's market capitalisation, which is not the Fama-French construction (that fixes market equity at a formation date). Both are fine for this lab. Neither is fine unstated.

5.6 Validate the panel before you use it

Run all of these. Each one has caught a real error in a student notebook.

Section 6 — Visualise it

Five rules for every chart in this course. They are not stylistic.

  1. Log scale for any multi-decade price or index series. On a linear axis, thirty years of compounding renders the first twenty as a flat line against the axis. A doubling in 1998 and a doubling in 2024 are the same event and must occupy the same vertical distance.
  2. Never a dual y-axis. Two measures on two scales in one frame lets you manufacture any apparent relationship by choosing the scales. Use two stacked panels sharing the x-axis.
  3. Leave the gap open. Do not interpolate across Dell's private years, and do not let matplotlib connect the last 2013 point to the first 2018 point. Plot the segments separately or insert NaN; a connecting line is a claim you did not make.
  4. Label the discontinuity on the chart. A reader who has to be told in the caption that the shaded band is a take-private will not be told.
  5. Colour carries identity, not rank. One colour per company, fixed, everywhere, including the fundamentals charts. If a filter changes which series are shown, the survivors keep their colours.

The two-colour palette below is checked for colour-vision deficiency separation; use it rather than matplotlib's default cycle, and pair it with direct labels so identity never rests on colour alone.

7.4 From two companies to your panel of 8–15

Apple and Dell were the worked example. Lab 2 wants 8 to 15 securities, and the number is deliberately small — this is not a data engineering exercise.

What does not change: the queries. PERMNOS is a tuple; make it longer. Every SQL statement takes IN %(p)s unchanged, the CCM link and its date-range validation work the same, and every assertion in Step 5.6 holds at any panel size. You do not need a new pipeline.

What does change is the judgement, and in two places a little code: resolving identifiers for names you cannot inspect by eye, and deciding what to do if one of your companies has two share classes trading at once.

What does change is what you can no longer do by eye.

Resolving identifiers. You cannot read fifteen name histories the way you read Dell's. Do it programmatically, then verify: one row per requested name, showing how many PERMNOs it resolved to, the coverage window, and the exchange. The names that resolve to more than one PERMNO, or to none, are the interesting ones — and a name that returns nothing will not appear in any null count.

The coverage table becomes the deliverable. At two companies it was a sanity check. At fifteen it is the Lab 2 Step 2 artefact, and the thing you will actually be defending.

PERMCO versus PERMNO. Two companies got you one clean case (DVMT and Class C sharing PERMCO 55676, though never on the same day). In a panel of fifteen you may have a company with two share classes trading simultaneously. Decide explicitly: keep only the primary security, or aggregate market capitalisation across the PERMNOs of that PERMCO — which is what WRDS's own Fama-French code does, and note that it aggregates per date, across eligible common-stock securities only, not across every PERMNO ever attached to the PERMCO. Either choice is defensible. Not noticing is not.

Delistings become plural. With fifteen names over thirty years you will likely have several, and some may have a null dlret. The default for this course: leave it missing and report the rate — "2 of 3 delistings have no delisting return" is the deliverable. Substituting a value (Step 3.5 names the standard ones) is optional, and if you do it, say so. You are not expected to adjudicate the literature on this.

Caching earns its keep. Fifteen names is still a small pull, but you will re-run the notebook many times. Step 1.5 exists for this.

Charts stop being one chart. Do not plot fifteen lines in one frame — beyond about six series, colours stop being distinguishable and the legend does the work the chart should be doing. Use small multiples, or plot a panel statistic and overlay only the two or three securities you are making a point about. The Section 6 rules are unchanged; the form is not.

A word on what you will find. Some of your names will be entirely well-behaved. It is perfectly possible to draw eight companies that all listed once, never renamed, never split off a subsidiary, and still trade. If that is your panel, say so — "I checked for X, Y and Z and found none" is a real result and reads as competence. What does not read as competence is a panel where nobody looked.

Section 9 — Irregularities: a gallery, not a to-do list

Everything below turned up while running the queries for this document. Almost none of it is resolved, and you are not expected to resolve it. This section is not an assignment bank. It is here so that when something like it happens to your company, you recognise the shape of it instead of assuming you broke something.

Two points, and they are the whole reason the section exists.

The data carries the company's history. Every oddity below is a corporate event, a vendor decision, or a file convention that left a mark. The five-year hole is a leveraged buyout. The CUSIP that changes mid-series is a rename. The adjustment factor that steps while the share factor does not is a spin-off. You are not looking at defects; you are looking at history, written in fields that were never designed to narrate it. Learning to read that is most of what separates someone who can use CRSP from someone who can query it.

The data is hard to handle, and it is hard case by case. There is almost no universal rule. Nearly every item below needs a judgement about this security, in this period, for this question — and the same field can be a nuisance in one analysis and disqualifying in another. That is precisely why data_quality_issues.md asks you to rate severity yourself rather than looking it up.

Your company may have none of these. It may have three that are not here. Two companies over a few hours produced this list; a different pair would produce a different one. Do not go looking for these specific items in your own data and conclude all is well when you do not find them.

What is actually expected of you: notice, write it down, decide whether it matters for what you are doing, and move on. If it blocks you, deal with it then — and "I noticed this, could not resolve it, and here is what it would change if it mattered" is a complete and professional answer.

Calibration. This course is seven weeks and it is exploratory by design. Nobody masters this material in a term. Practitioners work with CRSP and Compustat for years and still meet cases they have not seen before; the honest figure is closer to seven years than seven weeks. The goal here is recognition, not mastery — you should leave able to tell that something is odd, and to say so in writing. That is a genuinely useful professional skill and it is enough.
