Week 1 — Handout

Register: TEACH. Narrative and worked examples. The steps you hand in are in lab.md; conventions and licence rules are in rules.md.

You arrive with: a finance background, mixed programming experience, the names of some professional platforms, and whatever coding tools you already use. Nothing here assumes you can write Python from scratch.

Why this matters

An associate asks for a company's revenue history and a security's returns. Your university pays for research databases most people never open, and there are free sources that will answer in ninety seconds.

Ten minutes later you have a number. What decides whether you are useful is not that you got one — it is whether you can say where it came from, whether that source was the right one to ask, and whether the code actually did what you think it did.

Two things will happen today. Two sources will disagree about the same security, and only one of them is wrong. And you will find a defect in a commercial data feed using nothing but arithmetic.

Part 2 — Generation 2, in two minutes, for free

Start here, because you can do it right now with no account at all.

The SEC publishes every filing plus a structured data API. No key, no login — just a User-Agent header identifying you.

import json, urllib.request

req = urllib.request.Request(
    "https://data.sec.gov/submissions/CIK0001326801.json",
    headers={"User-Agent": "your.name@purdue.edu"})   # SEC requires a real contact
d = json.load(urllib.request.urlopen(req))

print(d["name"], d["tickers"])
for f in d.get("formerNames", []):
    print(f["name"], f["from"][:10], "->", f["to"][:10])
Meta Platforms, Inc. ['META']
Facebook Inc 2005-05-06 -> 2021-10-27

What just happened

0001326801 is a CIK — a permanent identifier. The ticker changed from FB to META. The CIK did not.

This is the idea professional data is built around, and it is the first genuinely professional habit to acquire: a ticker is a display label on an exchange, not an identity. Tickers get reassigned, reused, and changed. A ten-year series keyed on ticker would find no FB data after the changeover and no META data before it — two truncated series, neither of which looks broken.

Every professional dataset has its own permanent key: CRSP uses PERMNO, Compustat uses GVKEY, bond data uses CUSIP, the SEC uses CIK. Different key per dataset, which is why joining across them needs a link table rather than a ticker match.

Note the cost: nothing, and about ninety seconds.

Part 3 — Generation 1, and why it resists automation

WRDS is not a ticker API. It is a library of named research datasets on a PostgreSQL database, and you choose the dataset before the variable:

DatasetHoldsKeyed on
CRSPUS stock prices, returns, delistings, share countsPERMNO
Compustatcompany fundamentals from filingsGVKEY
TRACEcorporate bond transactionsCUSIP
IBESanalyst estimatesits own ticker

You reach it with pip install wrds, and mostly with SQL.

LSEG Workspace is Purdue's other institutional holding, available to every Purdue user. Its coding route is CodeBook — a Jupyter environment that runs as an app inside Workspace, in LSEG's cloud. Which programmatic access our licence includes is an open question, and Part 6 turns that into an exercise rather than an obstacle.

The extreme case: a source with no machine interface at all

Purdue's LSEG subscription includes Datastream as an add-on — over a century of historical time series, genuinely irreplaceable for long-horizon work.

Its interface is Excel. An add-in that puts a Workspace tab in your ribbon. Purdue describes no Python route, no API, no programmatic access of any kind. Downloads are capped at 30,000 values per request. Licences are scarce — faculty, graduate students, and research collaborators — and they are removed for inactivity.

So: a century of excellent data, reachable only by hand.

You cannot automate it at all. Not because the tooling is inadequate — because there is no interface to automate. That is a real constraint and you will meet it repeatedly, because a great deal of valuable institutional data lives behind interfaces built for humans.

The professional response is not to complain and not to pretend the source does not exist. It is to use it for what it is uniquely good at, work within the stated limits, and write down the manual procedure so someone else can repeat it. A hand extraction with a written procedure is reproducible. A hand extraction with no record is not, and the difference is entirely up to you.

Why it resists automation

SQL is the easy part. The hard part is the schema — the table names, the column names, the entitlements your institution actually bought. None of that is public. There is no reference you can look it up in from outside, which means anything writing a CRSP query without access to your WRDS instance is guessing, however well-formed the result looks.

Generation 1 was designed before machines were expected to drive it, and it shows. That is not a criticism of the data, which is often irreplaceable. It is a description of the work.

Part 4 — Source discipline

One habit, and it is not about any particular tool.

A claim about a data source is not documentation. Package names change, endpoints move, schemas get reorganised, coverage windows are narrower than advertised, and licence terms restrict things you would assume were fine. Anything can tell you otherwise with complete confidence — a blog post, a StackOverflow answer from 2019, a colleague, an assistant, your own memory of how it worked last term.

Before you rely on generated or remembered code against a source, check five things against the vendor's current documentation:

  1. Package — does it still exist under that name?
  2. Endpoint or table — is it in the current reference?
  3. Fields — do those column names exist?
  4. Coverage — does the source hold the period you asked for?
  5. Licence — does your agreement permit what this code does?

Step 5 is the one nobody runs, and it is the one with consequences. Nothing else on the list can get your institution's access revoked.

Worth trying once, because it is concrete: Thomson Reuters became Refinitiv, Refinitiv was acquired by LSEG, and the Python package was renamed refinitiv-data → lseg-data. The internet is full of code using the retired names. Search for "Refinitiv Python" and see how much of what you find is current — then check the vendor's documentation and see how long that takes. It is about two minutes, and it is the whole habit.

The rule. Verify the claim, not the claimant. This is true of every source of claims you will ever have, and it does not become less true when the claim is well written.

Part 5 — Find out what you are actually entitled to

Here is a real problem, unsolved, from this course's own preparation.

Your instructor wrote to the library asking exactly which programmatic access Purdue's LSEG licence includes — Data Library, Desktop Session, Platform Session with App Key or Service ID, the MCP connector, and which content entitlements.

No reply came. That is not unusual. It is the normal case.

So you diagnose it yourself. From Workspace web, search the app bar for APPKEY — if the App Key Generator opens, the APIs it offers to select are your answer. Search for CODEBOOK — if it opens, the hosted Python environment is entitled. Then check MyAccount, which holds the authoritative record of product, data, and exchange entitlements. Full procedure in [the source register](../sources.html).

Three things get conflated and they are separate:

App Keyidentifies your application
Session typeDesktop Session needs the desktop app running; Platform Session needs cloud credentials and is usually a separate enterprise entitlement
Content entitlementswhich data you may actually pull

You can hold a valid App Key and still be refused the content.

Why this is in the course rather than smoothed over. "What does my licence permit?" is a real professional question that routinely has no fast answer. The competent behaviour is to ask precisely and in writing, diagnose what you can yourself, keep the record, and design so you are not blocked while you wait. Nothing you are graded on this term depends on the answer.

Part 6 — Compute something, and state how

Data you cannot compute with is trivia. The quantity used all term:

\text{Total Return} = \frac{P_t - P_0 + \sum D_i}{P_0} = \underbrace{\frac{P_t - P_0}{P_0}}_{\text{price}} + \underbrace{\frac{\sum D_i}{P_0}}_{\text{income}}

NVDA, one year from 2024-06-10:

P0 = 121.79   (close, 2024-06-10)        dividends, by ex-date
Pt = 143.96   (close, 2025-06-10)          2024-06-11   0.01
                                           2024-09-12   0.01
price return  = (143.96-121.79)/121.79     2024-12-05   0.01
              = 0.182035 = 18.20%          2025-03-12   0.01
income return = 0.04/121.79                ------------------
              = 0.000328 =  0.03%          sum D   =    0.04
total return  = 0.182363 = 18.24%

Three basis points of income — exactly why you should not learn this formula on one security. Same window, two others:

                 P0        Pt     sum D    price     income     total
NVDA          121.79    143.96     0.04   18.20%      0.03%    18.24%
JNJ           147.13    156.45     5.02    6.33%      3.41%     9.75%
KO             63.59     72.35     1.97   13.78%      3.09%    16.87%

For JNJ, income is 3.41 of the 9.75 percentage points — over a third of what the holder earned. Quote price return on a dividend payer and call it performance, and you have understated the result by a third.

Two methods, and a gap that means something

Vendors publish an adjusted close that already contains income, so a simple ratio gives total return. Run both:

              price + dividends    adjusted close      gap
NVDA                    18.24%            18.24%     0.6 bp
JNJ                      9.75%             9.80%     5   bp
KO                      16.87%            17.18%    31   bp

They disagree, always in the same direction, and the gap grows with dividend yield. That pattern is the tell: the adjustment assumes each dividend is reinvested on its ex-date; the simple formula assumes it sits in cash. Reinvested income compounds.

Neither is wrong. A professional states which they used.

Reading the gap. A few basis points scaling with yield is the method difference, expected. A gap of two percent is a bug in your code.

Part 7 — Two sources, one security, one bad number

Now the judgment call, which no amount of tooling makes for you.

Same security, same six days, two independent sources. Source A is a commercial API (Financial Datasets). Source B is yfinance.

SOURCE A                                          SOURCE B
date         open    high     low   close         open      high      low     close
2024-06-07 119.77  121.69  118.02  120.89       119.770   121.692  118.022  120.888
2024-06-10 120.37  195.95  117.01  121.79       120.370   123.100  117.010  121.790
2024-06-11 121.77  122.87  118.74  120.91       121.770   122.870  118.740  120.910

Every open, low, and close agrees to the penny. One field, on one day, does not. Source A reports a high of 195.95; Source B reports 123.10.

Catch it with arithmetic alone

You will not always have a second source. This row contradicts itself:

high / max(open, close) = 195.95 / 121.79           = 1.609   -> 61% above the close
(high - low) / low      = (195.95-117.01) / 117.01  = 0.675   -> a 67% intraday range
open-to-close move      = (121.79-120.37) / 120.37  = 0.012   -> the stock moved 1.2%

A security does not trade in a 67% range on a day it closes 1.2% from its open. No external source was needed to know that.

Where it sits matters. 2024-06-10 is NVDA's 10-for-1 split date. Vendor pipelines break where the adjustment logic runs. When hunting bad data, look at split, spin-off, and merger dates first.

The difference that is not an error

Volume the same day: 314,162,650 against 313,434,100 — a gap of 0.23%, and every other day differs slightly too.

Not a defect. US equities trade across many venues and vendors differ in which prints they consolidate. Two honest sources routinely disagree about volume by fractions of a percent.

This is the whole skill. One disagreement you must reject; one you must document and move on from. They look identical in a diff.

Part 8 — Writing it down so it runs again

You will produce a number today. In six weeks you will need to produce it again, on a different machine, and explain how you got it. That is not a documentation chore bolted on at the end — it is a property of how you write the code in the first place.

Four habits, starting this week. They cost nothing now and are expensive to retrofit.

Fresh kernel, top to bottom. A notebook that only runs because of a variable defined in a cell you later deleted is not a result, it is a memory of one. Restart and run all before you believe anything.

No hand-typed numbers. Every figure in a write-up traces to a line of code that produced it. The moment you copy a number out of an output cell and paste it into prose, it stops being connected to the data and starts being a claim about the past.

Keys never go in code. Use an environment variable or Colab's secrets. An API key committed to a notebook is a security incident, and the fix is to rotate the key, not to delete the cell.

A function the second time you need it. The first copy-paste is efficient. The third is how a bug gets into your work three times and fixed once.

def total_return(p0, pt, dividends):
    """Total return over a holding period. Dividends assumed held in cash."""
    return (pt - p0 + sum(dividends)) / p0

That docstring is doing real work: it records the convention. Six weeks from now, when your number disagrees with someone else's, the first question will be which assumption each of you made — and one of you will be able to answer immediately.

The rule. Write it so it runs again. Every week of this course consumes the previous week's output, and Week 7 is graded on whether a colleague can rerun the whole thing.

Part 9 — Directing an assistant, and the four choices hiding in one number

Ask an assistant for "ABG's PEG ratio" and you get one number. Ask four analysts and you get four, all defensible. The difference is not skill. It is that PEG is not a measurement — it is the output of four choices you make before you compute anything, and most published versions never tell you which four.

This part teaches the method you will use for the rest of the term. Four mechanisms.

1. Decompose before you source

PEG = P/E divided by a growth rate. That is not one data problem, it is three: a price, an earnings figure, and a growth figure.

Three terms, in case they are not yet second nature. EPS is earnings per share — net income divided by the share count. Diluted EPS uses a larger share count that assumes options and convertibles are exercised, so it is the more conservative of the two; use it consistently. A buyback is a company purchasing its own shares, which reduces the share count and therefore raises EPS even when total earnings are flat. Each comes from somewhere different, each has its own conventions, and each can be wrong on its own.

Naming a source before decomposing is how you end up with a number you cannot defend. Decompose first, then source each primitive separately.

2. Know where each primitive lives — and where it cannot come from

Everything below is the guaranteed lane: a price from yfinance, earnings from the company's own filing through SEC EDGAR. No account, no cost.

Price. ABG, close of 2026-08-21: $214.75.

Earnings. From ABG's FY2025 10-K (accession 0001144980-26-000051, filed 2026-02-20):

FY2025   net income   $492.0m    diluted EPS   25.13    diluted shares   19.6m
FY2024   net income   $430.3m    diluted EPS   21.50    diluted shares   20.0m
FY2023   net income   $602.5m    diluted EPS   28.74    diluted shares   21.0m

Growth. Here is the one that matters: no filing contains forward growth. A 10-K reports what happened. It has no field for what will happen. So if a data feed hands you a growth rate, something estimated it — and unless the feed says whose estimate, over what horizon, on what basis, you cannot defend the number that comes out.

That is the structural limit. EDGAR can give you E and can never give you G. Say that out loud, because an assistant will not volunteer it.

3. Cross-check a fixed minimum

Two independent sources per primitive, minimum, every time — on any lane. Record each with its retrieval date and its definitional choices. Not "as many as you can get": a fixed floor, so your work is comparable to everyone else's regardless of what you have access to.

Where a second source is unavailable to you, that attempt is documented and counts. An unavailable source is a finding about the source, not a gap in your work.

4. Recompute, then compare

Compute the headline figure from your own primitives. Then look at any published version. Where they disagree, the disagreement is the finding.

The percentage-point convention, because it eats people. A growth rate of 16.88% enters the PEG formula as 16.88, not as 0.1688. Feeds store it as a decimal; the formula wants points. Get this backwards and your PEG is off by a factor of 100 and still looks like a number.

The cross-check, worked

Mechanism 3 says two independent sources per primitive. Here is what that actually looks like, with the digits, before you are asked to do it.

PrimitiveSource 1Source 2Verdict
PriceMarket quote, 2026-08-21 19:59:58Z: 214.75The same feed's market capitalisation, $3,855.2mConsistent — but read on
Earnings per shareABG FY2025 10-K, filed 2026-02-20, diluted EPS 25.13A commercial feed's standardised TTM EPS 27.84Differ, and neither is wrong
GrowthComputed from the 10-K: +16.88% one-year EPSThe same feed's growth field: +1.57%Differ on basis

The price row is the interesting one. Divide the market capitalisation by the price: 3,855.2m / 214.75 = 17.95m shares. But the 10-K reports 19.6m weighted-average diluted shares. Those do not match, and that is not an error either: weighted-average diluted shares are an average across the fiscal year, while market capitalisation uses shares outstanding today — and ABG has gone on buying its own shares. The cross-check did not find a defect. It surfaced a definitional difference that would have silently corrupted any per-share figure built from the wrong one. That is what cross-checks are for.

A third source for growth does not exist on the free lane. Forward growth needs an estimates database — IBES, reachable through WRDS. If your account is still queued, that attempt is recorded, not skipped:

Source: IBES consensus long-term growth, via WRDS Route attempted: Purdue Libraries WRDS request form, submitted 2026-08-20 Date of attempt: 2026-08-24 Barrier observed: account pending departmental approval; no data access Why it would have been independent: IBES aggregates sell-side analyst estimates, which are forward-looking and produced outside the company — unlike every figure above, all of which derive from ABG's own filing or from one vendor's processing of it.

A record like that counts as a source attempt. A bare "could not access WRDS" does not — it tells the reader nothing about what was missed or how much it mattered.

The same company, the same day, four answers

P/E from our primitives: 214.75 / 25.13 = 8.546.

Which growth, from the filingsGrowthPEG
One-year EPS growth, FY2024 → FY2025+16.88%0.51
One-year net income growth, FY2024 → FY2025+14.34%0.60
Two-year EPS CAGR (compound annual growth rate), FY2023 → FY2025−6.49%−1.32
A commercial feed's published PEG, same day — supplied below, not computed by you1.57%4.91

Work through what each row is telling you.

Rows 1 and 2 differ because of buybacks. Net income grew 14.34%, EPS grew 16.88%. EPS grew faster because the diluted share count fell from 20.0m to 19.6m — the same earnings spread over fewer shares. Neither figure is wrong. They answer different questions: row 2 asks how the business did, row 1 asks how a shareholder did.

Row 3 is a different window, and it changes the sign. FY2023 diluted EPS was 28.74; FY2025 was 25.13. A CAGR — compound annual growth rate — is the single yearly rate that would take you from the first figure to the last over that many years. Over two years: (25.13 / 28.74) (1/2) - 1 = -0.0649, or −6.49% a year**. Over two years, EPS fell. Over the last one, it rose sharply. Both are true, and the growth window alone decides whether ABG looks cheap or looks like a company in decline. PEG on a negative growth rate is meaningless — which is why you will rarely see row 3 published.

Row 4 is the one to interrogate — and it is handed to you. These three figures come from a commercial data feed (Financial Datasets, retrieved 2026-08-22). They are supplied evidence: reproducing them needs an API key, so nothing in this course requires you to obtain them. What the course does require is that you can interrogate a number someone hands you.

Its PEG is 4.91 and its P/E is 7.7133 — the feed's own unrounded figure, which is why we can invert it precisely — against our 8.546. Invert it: 214.75 / 7.7133 = 27.84. So that feed's earnings figure is 27.84 per share, not the filed 25.13 — it is using a trailing-twelve-month EPS that spans parts of two fiscal years, while we used the fiscal year as filed. Its growth input, 1.57%, matches none of the filed figures for the same reason.

Nothing here is a defect. Every number is correctly computed from a stated basis. The defect would be reporting any one of them without saying which basis — and that is what an assistant does by default.

What this makes you able to do

An assistant told "get me ABG's PEG" returns 4.91 and stops. An assistant directed with the four mechanisms above returns 0.51, 0.60, −1.32 and 4.91, says which choice produced each, and names the one thing none of them can supply from a filing: forward growth.

That difference is the whole course in one number. Lab Step 8 asks you to write the instructions that produce the second behaviour.

The wider landscape — what exists beyond what you can reach

Two generations is the distinction that organises this course. It is not the whole market, and you should not leave Week 1 believing Purdue's licences are the boundary of what exists. The seat you take next year will have a different set, and part of being useful in it is knowing what to ask for.

The full register is in [the source register](../sources.html). The shape of it:

The institutional tier — Bloomberg, FactSet, S&P Capital IQ, MSCI, Morningstar Direct, PitchBook, Preqin, ICE, Moody's, BlackRock's Aladdin. Some Purdue has, most it does not. These are sold to institutions, priced accordingly, and several are not scriptable at all. Knowing what each is for is worth more to you right now than access to any of them.

The API-native tier — Polygon, Tiingo, Alpha Vantage, Financial Modeling Prep, Intrinio, Finnhub, Nasdaq Data Link, Databento, Alpaca. Purdue does not need to license these; you can hold a key yourself, and most have a free tier. This is the tier where a student can build something real without an institution behind them.

The free and open tier — and the one most students under-use. The Ken French Data Library holds the canonical factor returns that most published research runs on. Open Source Asset Pricing publishes replicated cross-sectional predictors with the code. FRED holds the macro and the risk-free series behind every Sharpe ratio you will compute. None of it costs anything, and none of it is lower quality than the paid tiers for what it covers.

A source is a counterparty, not a fact of nature

IEX Cloud was a popular, developer-friendly market-data API that a great many people built on. It announced retirement on 31 May 2024 and shut down on 31 August 2024. The exchange still operates; the data subsidiary does not.

Two consequences worth carrying out of this week.

Code written against one vendor inherits that vendor's business decisions. Anything you intend to rerun in a year should survive its source disappearing — which in practice means a documented second source you could switch to. That is a second reason for the two-source rule, beyond catching errors.

Tutorials outlive the services they teach. Search for market-data examples today and you will still find IEX Cloud code, confidently written, that cannot run. An assistant trained on that corpus will reproduce it for you without hesitating. This is the concrete form of the rule you will meet all term: an AI's knowledge of a data source is a claim, not documentation.
